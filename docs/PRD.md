# QA_Agent 产品需求文档

## 1. 文档信息

- 文档名称：`QA_Agent` 产品需求文档
- 文档版本：`v2.0`
- 文档状态：重构演进版
- 面向对象：产品、设计、前端开发、后端开发、Agent 工程实现
- 文档目标：明确 `QA_Agent` 当前阶段的产品定位、核心资产、技术方向、功能模块和版本演进规律，为后续分阶段研发提供统一依据

本文适用范围为 `QA_Agent` 当前这一轮重新收敛后的产品设计，不再默认首版一次性交付完整的生成、反馈、评分、记忆闭环，而是按照“核心资产 -> RAG -> 生成 Agent -> 反馈 Agent -> 评分 Agent -> Memory”的顺序逐步推进。

## 2. 产品概述

### 2.1 项目名称

`QA_Agent`

### 2.2 产品定位

`QA_Agent` 当前定位为一套面向技术面试准备场景的训练工作台。它不是通用聊天工具，也不是泛化题库平台，而是一套围绕用户资料、问答集和训练闭环展开的可复用资产系统。

产品的核心不是“让 AI 自由发挥”，而是让系统基于用户真实资料，逐步沉淀出可管理、可复用、可训练、可迭代的核心资产，并在此基础上分阶段挂接生成、反馈、评分和记忆能力。

### 2.3 当前核心问题

当前版本聚焦解决两个连续问题：

1. 如何把用户资料稳定沉淀为结构清晰、长期可用的训练资产，而不是一次性生成结果。
2. 如何在资产底座稳定之后，再逐步接入真正可用的 Agent 能力，而不是一开始就让系统承担过大的智能链路复杂度。

围绕这一核心问题，当前产品必须同时满足以下要求：

1. 资料必须是系统的主证据源，而不是可有可无的输入附件。
2. 问答集必须是可编辑、可持续训练、可长期复用的核心资产，而不是一次性文本输出。
3. 系统演进必须遵循阶段化规律，先做底座，再做智能链路，不再走首版大而全路线。

### 2.4 核心价值主张

1. 把用户已有资料转成结构化、可复用的问答训练资产。
2. 让用户围绕同一份问答集持续练习，而不是每次重新开始。
3. 在资产稳定的前提下，逐步引入生成、反馈、评分与记忆能力，形成真正可持续的面试训练工作台。

## 3. 目标用户与使用场景

### 3.1 目标用户

当前目标用户明确收敛为正在准备技术面试、手中已经有一定学习资料沉淀的人群，尤其是以下三类用户：

1. 已有 `Markdown` 项目资料、学习笔记、面试整理，但不会系统沉淀训练资产的人。
2. 希望围绕自己资料开展高频训练，而不是刷泛化题库的人。
3. 希望未来能借助 Agent 提升训练效率，但当前首先需要稳定资产底座的人。

### 3.2 用户典型资料形态

当前用户最常见的输入资料包括：

1. 项目总结文档
2. 中间件学习笔记
3. 面试高频题整理
4. 八股复习提纲
5. 自己写的技术知识总结

当前阶段正式支持的资料输入格式以 `Markdown` 为主。

### 3.3 典型使用场景

当前产品的典型使用场景按演进路径可以拆成以下几步：

1. 用户首次进入产品，建立账户并完善唯一全局 `Profile`。
2. 用户上传并管理自己的资料，形成可复用资料库。
3. 用户基于资料库构建问答集和题目单，先完成资产层闭环。
4. 系统在后续版本中逐步引入生成 Agent，让问答集生成从假数据驱动转向真实智能链路驱动。
5. 用户围绕问答集开展顺序、随机或按模块练习。
6. 系统在后续版本中逐步引入反馈 Agent、评分 Agent 和 Memory，形成更完整的训练闭环。

### 3.4 当前主使用路径

当前产品主路径不是“先聊天再生成”，而是：

1. 完善 `Profile`
2. 建立资料库
3. 建立问答集
4. 管理题目单
5. 进入练习
6. 后续再接入 Agent 能力

## 4. 产品目标与成功标准

### 4.1 当前阶段产品目标

当前阶段的产品目标不是一次性完成完整智能训练系统，而是分阶段建立以下能力：

1. 建立稳定的核心资产模型，包括资料库、问答集、题目单和练习会话。
2. 建立支持后续 Agent 演进的数据底座，包括结构化资料、切片与检索基础。
3. 用可控、可拆分、可追踪的方式逐步接入 RAG、生成、反馈、评分和 Memory。

### 4.2 当前阶段成功标准

当前阶段的成功标准按版本推进，而不是统一压到首版。

#### 阶段一成功标准

1. 用户能够完成资料、问答集、题目单的创建、编辑、删除与查看。
2. 资产之间的关系清晰稳定，能够支撑后续真实 Agent 接入。
3. 前端不依赖真实 Agent 也能完整跑通核心资产工作流。

#### 阶段二及以后成功标准

1. `RAG` 能提供稳定、可复用、可验证的资料证据召回能力。
2. 生成 Agent 能把资料转为结构化问答集，而不是泛化文本。
3. 反馈 Agent 和评分 Agent 能围绕真实问答资产产生稳定结果。
4. `Memory` 能在不污染主链路的前提下提升长期训练效果。

### 4.3 高质量 `Q&A` 标准

后续版本中，对“高质量 `Q&A`”的判定以以下标准为主：

1. 高度贴合用户资料，而不是脱离资料自由发挥。
2. 有明确证据边界，不把无依据内容包装成确定事实。
3. 同时适合学习回顾与口头表达，兼顾知识笔记和面试回答两种用途。
4. 能进入后续反馈、评分和长期训练流程，而不是停留在一次性输出层。

### 4.4 非目标

当前阶段明确不做以下方向：

1. 不做面向所有岗位的通用题库平台。
2. 不做开放式闲聊型 AI 工具。
3. 不在第一阶段追求完整 Agent 闭环一次落地。
4. 不在第一阶段引入复杂 `Memory`、复杂行为分析和复杂审计体系。
5. 不为了“看起来更智能”而牺牲证据可信度和资产稳定性。

## 5. 技术选型

### 5.1 前端技术选型

前端当前直接延续现有 `frontend` 工程方向，不重新推翻重做。原因如下：

1. 当前前端页面结构已经具备 `Profile`、资料库、问答集、练习、结果等核心资产工作流。
2. 当前阶段真正的问题不在于前端框架，而在于后端链路和整体演进顺序。
3. 保持前端稳定，有利于把研发重心集中到核心资产模型、RAG 底座和后续 Agent 链路上。

因此，前端当前原则是：

1. 保留现有 `frontend`
2. 优先围绕真实数据模型对接
3. 不在这一轮重新发明前端架构

### 5.2 后端技术选型

后端当前拟采用以下技术方向：

1. `LangChain4J`
2. `MySQL`
3. `MyBatis-Plus`
4. `Kafka`
5. `PostgreSQL`
6. `Redis`

### 5.3 后端选型原则

#### `LangChain4J`

用于承接后续 Agent `DAG` 编排和模型调用能力。当前选择它的原因不是因为“要做通用 Agent 平台”，而是因为后续生成、反馈、评分都需要更清晰的链路式 Agent 组织方式。

#### `MySQL`

用于承载主业务数据。当前核心资产如账户、画像、问答集、题目、练习会话等数据，都更适合作为标准业务数据稳定落在 `MySQL` 中。

#### `MyBatis-Plus`

用于后端数据访问层建设。当前选择它的原因是：

1. 便于快速重建主业务 CRUD
2. 对第一阶段核心资产开发效率更高
3. 更适合这一轮以业务重构为主的节奏

#### `Kafka`

用于承载异步任务和阶段性消息流，特别是：

1. 问答集创建任务
2. 后续 Agent 链路异步处理
3. 多阶段任务消息推进

#### `PostgreSQL`

用于承载结构化资料切片和后续 `RAG` 所需能力。结合最新 `table.md`，`PostgreSQL` 更适合负责：

1. 文档切片
2. 向量检索
3. 检索型中间数据

#### `Redis`

用于承载缓存能力，减少主业务查询和阶段性重复计算开销，重点服务：

1. 读取高频资产数据
2. 任务阶段状态缓存
3. 检索前置结果缓存

### 5.4 技术组合结论

当前技术选型并不是为了追求“堆技术栈”，而是为了匹配新的产品演进顺序：

1. `MySQL` 负责主业务资产
2. `PostgreSQL` 负责结构化资料与检索底座
3. `Kafka` 负责异步链路
4. `Redis` 负责性能与缓存
5. `LangChain4J` 负责 Agent `DAG` 演进

## 6. 功能需求

### 6.1 Profile

#### 6.1.1 功能定位

`Profile` 是用户唯一全局画像，不是可有可无的设置页。它承担两类职责：

1. 个人基本信息管理
2. 智能体默认上下文配置

#### 6.1.2 业务目标

`Profile` 需要完成以下目标：

1. 保存用户的求职方向与基本背景
2. 组成生成、反馈、评分的默认提示词上下文
3. 允许用户对智能体行为做基础自定义
4. 成为后续长期记忆沉淀的高优先级显式输入

#### 6.1.3 关键字段

当前 `Profile` 重点围绕以下字段展开：

1. 目标岗位
2. 目标领域
3. 目标公司
4. 是否允许补充通用知识
5. 是否允许使用 Web 搜索
6. 答案风格
7. 反馈风格
8. 年龄
9. 年级
10. 专业
11. 当前准备阶段

#### 6.1.4 设计要求

1. 一个账号只允许一份全局 `Profile`。
2. `Profile` 的内容应被视为后续 Agent 的默认提示词上下文。
3. 第一阶段不要求 `Profile` 自动演化，只要求用户显式配置稳定可用。
4. 后续 `Memory` 接入时，`Profile` 应作为最高优先级的用户显式记忆输入。

### 6.2 核心资产

#### 6.2.1 核心资产定义

当前产品先围绕三类核心资产展开：

1. 问答集
2. 资料库
3. 题目单

这三类资产比 Agent 更重要，因为它们决定了系统是否真正可复用。

#### 6.2.2 资料库

资料库的作用不是上传临时附件，而是沉淀可复用资料资产。它至少要具备以下能力：

1. 上传资料
2. 查看资料
3. 编辑资料
4. 删除资料
5. 保存资料正文
6. 保存资料级摘要和模块结构
7. 支撑后续结构化解析和切片

当前阶段的正式输入以 `Markdown` 为主。

#### 6.2.3 问答集

问答集是产品核心资产，不是一次性输出。它至少要具备以下能力：

1. 创建问答集
2. 查看问答集
3. 编辑问答集
4. 删除问答集
5. 记录关联资料
6. 作为后续练习和 Agent 反馈的主工作对象

#### 6.2.4 题目单

题目单是问答集内部的最小训练单元集合。每个题目至少应包含：

1. 问题
2. 知识笔记
3. 标准回答
4. 模块标签
5. 难度
6. 证据边界提示
7. 来源切片引用

#### 6.2.5 资产关系要求

当前资产关系按以下规则设计：

1. 一份资料可以被多个问答集复用。
2. 一个问答集可以引用多份资料。
3. 一个问答集下包含多道题目。
4. 题目从属于问答集，不做全局题库。

#### 6.2.6 当前阶段重点

第一版本的产品重点不是先完成真实 Agent，而是先完成这些核心资产的完整 CRUD 和关系建模，并先用假数据跑通前端主链路。

### 6.3 Agent DAG 设计

#### 6.3.1 总体原则

后续 Agent 能力不采用一个“大而全”的自由智能体，而采用多个职责清晰的 `DAG` Agent：

1. 生成 Agent
2. 反馈 Agent
3. 评分 Agent

每个 Agent 只负责单一目标，不互相混用职责。

#### 6.3.2 生成 Agent

生成 Agent 负责把资料转成问答集。它的职责是：

1. 读取资料和 `Profile`
2. 规划题集结构
3. 检索证据
4. 起草题目
5. 校验输出
6. 形成最终问答集

推荐链路形态：

1. `plan`
2. `search`
3. `draft`
4. `validate`
5. `finalize`

#### 6.3.3 反馈 Agent

反馈 Agent 负责单题训练后的即时反馈。它的职责是：

1. 判断用户回答结果
2. 给出简洁反馈
3. 给出缺失点和改进方向
4. 引用相关证据

它不负责整轮评分，也不负责题目生成。

#### 6.3.4 评分 Agent

评分 Agent 负责整轮练习后的总结性评分。它的职责是：

1. 汇总会话结果
2. 给出整轮得分
3. 识别优势与薄弱点
4. 输出复习顺序和整体总结

它不负责单题即时反馈，也不负责题目生成。

#### 6.3.5 DAG 设计要求

三个 Agent 的 `DAG` 设计应满足以下要求：

1. 阶段清晰
2. 输入输出明确
3. 可追踪
4. 可回放
5. 可阶段化展示
6. 可单独演进

当前 `PRD` 不下沉到具体代码实现，但要求后续技术设计始终遵循“单 Agent 单职责”的原则。

### 6.4 RAG 支持

#### 6.4.1 功能定位

`RAG` 在当前产品中不是装饰能力，而是后续 Agent 真正可用的证据底座。它的目标不是简单做一个向量搜索，而是为生成、反馈、评分提供稳定、可信、可解释的资料召回能力。

#### 6.4.2 当前问题判断

市面上很多所谓 `RAG` 方案的问题在于：

1. 只做向量检索，忽略章节结构
2. 只做关键词匹配，忽略语义召回
3. 检索结果不稳定，无法支撑 Agent 长链路
4. 不考虑证据边界，导致内容看似完整但不可信

#### 6.4.3 当前设计要求

真正可用的 `RAG` 应至少满足以下要求：

1. 资料先结构化，再检索
2. 检索对象不是整篇文档，而是可管理切片
3. 同时支持语义召回与结构过滤
4. 召回结果要能明确指向资料来源
5. 检索结果应服务不同 Agent，而不是只服务生成

#### 6.4.4 可行策略

当前可行的 `RAG` 方向应综合以下策略：

1. 文档结构化切片
2. 标题路径保留
3. 模块标签过滤
4. 向量检索
5. 关键词检索
6. 混合召回
7. 召回后重排序
8. 基于 Agent 任务目标的证据裁剪

#### 6.4.5 效率目标

`RAG` 的设计不应只看召回率，也要看工程效率：

1. 切片要能复用，不每次重建
2. 检索路径要能缓存
3. 召回结果要能重复消费
4. 不同 Agent 要能共用同一套资料底座

### 6.5 Memory & History 支持

#### 6.5.1 功能定位

`Memory` 与 `History` 是后续演进能力，不是第一阶段强行落地项。但当前 `PRD` 必须先定义清楚它未来要解决什么问题，避免后续设计失焦。

#### 6.5.2 设计目标

后续 `Memory` 需要支持以下几类能力：

1. 长段记忆
2. 关键记忆
3. 薄弱模块记忆
4. 强势模块记忆
5. 阶段性历史回顾

#### 6.5.3 参考原则

后续设计应参考 `Harness Engineer` 这类强调“高价值记忆管理”的思路，避免把 Memory 做成无边界垃圾桶。其核心原则应包括：

1. 只保存对后续行为真正有价值的记忆
2. 明确区分显式信息与系统推断信息
3. 区分长期稳定记忆和短期历史片段
4. 记忆服务于训练效果，而不是服务于“看起来更聪明”

#### 6.5.4 长段记忆

长段记忆用于保存用户较稳定、可跨阶段复用的信息，例如：

1. 求职方向
2. 表达风格偏好
3. 资料主题结构
4. 阶段性能力画像

#### 6.5.5 关键记忆

关键记忆用于保存少量但高优先级的信息，例如：

1. 用户明确声明的重要目标
2. 明显错误高频点
3. 必须避免的表达问题
4. 某些需要持续强调的知识盲区

#### 6.5.6 薄弱模块记忆

薄弱模块记忆用于识别用户持续训练中的弱项，例如：

1. 连续答错的模块
2. 高频“不会”的模块
3. 经常只能答到一半的模块

#### 6.5.7 强势模块记忆

强势模块记忆用于识别用户已经稳定掌握的部分，从而：

1. 降低重复训练权重
2. 优先把资源让给薄弱项
3. 辅助后续评分与训练排序

#### 6.5.8 当前阶段边界

当前版本先不正式落地 `Memory`，但后续设计时必须遵循以下原则：

1. `Profile` 是显式记忆入口
2. 练习会话是历史信息入口
3. 问答集和题目是记忆挂载对象
4. `Memory` 必须建立在真实资产与真实历史基础上

## 7. 非功能需求

### 7.1 性能与响应

1. 第一阶段核心资产 CRUD 应保持稳定响应。
2. 资料查询、问答集查询、题目查询和练习会话查询应优先保证主路径流畅。
3. 后续 `RAG` 和 Agent 接入后，长任务必须采用异步链路，不阻塞主交互。

### 7.2 数据一致性与可靠性

1. 资料、问答集、题目、练习会话之间的关系必须清晰稳定。
2. 删除问答集时，相关练习数据需按设计规则同步清理。
3. 资料切片与资料正文必须保持一致，不允许长期漂移。

### 7.3 可维护性与可扩展性

1. 核心资产模型必须优先稳定，便于后续 Agent 链路挂接。
2. 数据结构必须支持从假数据阶段平滑过渡到真实 Agent 阶段。
3. 各 Agent 能力必须可独立开发、独立替换、独立调优。

### 7.4 检索效率与召回稳定性

1. `RAG` 不能只追求“能搜到”，还要追求“可稳定复现”。
2. 检索结果需要兼顾速度、结构感知和证据边界。
3. 检索层应尽量复用已有结构化资料和切片结果，避免重复建设。

### 7.5 输出可信度与证据边界

1. 生成、反馈、评分都必须优先依赖资料证据。
2. 当系统补充通用知识时，必须能够区分资料内信息和补位信息。
3. 不允许为了语言完整性而强行制造确定性结论。

### 7.6 DAG 可追踪性

1. 每个 Agent 链路应具备明确阶段。
2. 阶段消息应可记录、可回看、可恢复。
3. 阶段状态应能支撑前端展示和问题排查。

### 7.7 成本控制

1. 当前产品演进必须控制模型调用成本。
2. 第一阶段先做资产与底座，不直接引入重型智能链路。
3. 后续 RAG、生成、反馈、评分都要优先复用已有结构化结果与阶段数据。

### 7.8 安全性与数据隔离

1. 用户资料必须按用户维度隔离。
2. 问答集、题目、练习会话必须按用户隔离访问。
3. 账户状态控制必须可靠。
4. 后续引入 Memory 时，也必须遵循同样的数据隔离原则。

## 8. 版本规划

### 8.1 `V1`：核心资产 CRUD

#### 版本目标

完成核心资产层的稳定建模与前端可用闭环。

#### 版本范围

1. 完成 `Profile`、资料库、问答集、题目单、练习会话的基本 CRUD
2. 前端先填充假数据
3. 不接入真实 Agent 链路

#### 版本产出

1. 用户能完整使用核心资产工作台
2. 核心数据模型稳定
3. 为后续真实链路预留数据底座

### 8.2 `V2`：RAG 设计与落地

#### 版本目标

完成真正可用的 `RAG` 设计与落地。

#### 版本范围

1. 完成资料结构化解析
2. 完成切片与向量化
3. 完成混合召回和结构感知检索
4. 不止停留在简单向量检索或简单关键词检索

#### 版本产出

1. 后续 Agent 可复用的证据底座
2. 稳定的资料召回能力
3. 支撑生成、反馈、评分的统一检索基础

### 8.3 `V3`：生成 Agent DAG

#### 版本目标

完成生成 Agent 的链路式构造。

#### 版本范围

1. 建立生成任务主链路
2. 建立阶段消息流
3. 把资料转成真实问答集

#### 版本产出

1. 真实生成链路
2. 稳定问答集落库能力
3. 可追踪的生成阶段状态

### 8.4 `V4`：反馈 Agent DAG

#### 版本目标

完成单题反馈 Agent 的链路式构造。

#### 版本范围

1. 接入单题反馈链路
2. 输出判定、原因、建议和证据引用
3. 与练习会话结合

#### 版本产出

1. 可用的逐题反馈能力
2. 更稳定的训练体验

### 8.5 `V5`：评分 Agent DAG

#### 版本目标

完成整轮评分 Agent 的链路式构造。

#### 版本范围

1. 汇总练习会话结果
2. 输出整轮得分与准确率
3. 输出整体总结、优势、薄弱点和复习顺序

#### 版本产出

1. 可用的整轮评分能力
2. 更完整的训练闭环出口

### 8.6 `V6`：Memory 设计

#### 版本目标

完成 `Memory` 与 `History` 的正式设计与接入。

#### 版本范围

1. 建立显式记忆入口
2. 建立薄弱模块与强势模块记忆
3. 建立阶段性历史沉淀机制

#### 版本产出

1. 更长期的训练上下文能力
2. 更稳定的个性化训练体验

### 8.7 `V7`：暂定

#### 版本目标

根据前六个版本的实际运行效果，再确定下一阶段演进方向。

#### 当前预留方向

1. 更细的训练策略优化
2. 更复杂的记忆策略
3. 更强的资产管理能力
4. 更完整的 Agent 协作能力

## 9. 结论

这次 `PRD` 调整的核心结论只有一条：`QA_Agent` 不能再沿着“首版一次做完所有智能能力”的思路推进。

当前版本必须遵循以下演进原则：

1. 先把核心资产做好
2. 再把 `RAG` 做稳
3. 再分阶段接入生成、反馈、评分 Agent
4. 最后再引入 `Memory`

只有这样，系统才能从一个实现效果不稳定的“大而全原型”，逐步演进成真正可用的技术面试训练工作台。
