# V7 快速迭代设计说明

## 1. 文档目标

本文定义 V7 阶段优先快速迭代的四个需求：

1. 练习结果页数据可视化优化
2. AI 补全时允许用户指定标准答案
3. 练习题目自定义筛选
4. 语音输入答题

V7 的目标不是引入新的核心资产模型，而是在现有问答集、练习会话、反馈评估和补全链路之上，提升训练体验、结果可读性和手动资产维护效率。

## 2. 总体设计原则

### 2.1 优先保持现有主链路稳定

V7 不改变以下核心链路：

```text
qa_set / qa_item
  -> practice_session / practice_session_item
  -> FeedbackAgent
  -> AssessAgent
  -> ResultPage / ReviewPage
```

本次所有新增能力都应以兼容方式接入：

1. 语音输入只改变前端输入方式，不改变后端判分协议。
2. 结果页可视化优先复用现有 `PracticeDetailResponse` 与 `PracticeSessionResponse`。
3. 标准答案补全继续使用 `/qa/item/complete` 作为统一入口。
4. 自定义筛选通过标准化练习创建协议实现，不改变 Quiz 页整本题集练习语义。

### 2.2 用户输入优先于 AI 生成

当用户在补全阶段提供标准答案时，该答案就是人工裁定的 ground truth。AI 只负责补齐辅助字段，不得改写、替换或润色用户标准答案。

### 2.3 练习会话以题目快照为准

练习开始时，后端仍把题目内容写入 `practice_session_item` 快照字段。即使用户选择了正在 AI 补全中的题目，也允许创建练习；该轮练习使用创建时刻的快照内容。

## 3. 需求一：练习结果页数据可视化优化

### 3.1 问题判断

当前 `ResultPage` 已经展示平均分、达标率、五维数量、优势、薄弱点、复习建议和逐题明细，但核心信息仍以文本和数字卡片为主。用户需要快速回答三个问题：

1. 本轮整体答得怎么样？
2. 哪些模块最弱？
3. 最近几次是否有进步？

因此，V7 结果页可视化重点不是堆叠图表，而是把现有结构化结果转成更直观的诊断视图。

### 3.2 推荐图表

| 区域 | 图表 | 数据来源 | 价值 |
| --- | --- | --- | --- |
| 总体表现 | 分数环 + 五维堆叠条 | `session.score`、`session.accuracy`、五维 count | 一眼看整体水平和结果结构 |
| 模块表现 | 横向条形图 | `items[].moduleTag`、`items[].score`、`items[].result` | 找出薄弱模块和稳定模块 |
| 题目分布 | 题目结果矩阵 | `items[].result`、`items[].score`、题目顺序 | 快速定位错误密集区 |
| 历史趋势 | 折线图 | `/practice/session/history` | 判断同一题集练习走势 |

### 3.3 前端处理

结果页前端负责从现有详情数据聚合本轮图表数据：

1. 五维分布直接读取 session count。
2. 模块表现按 `moduleTag` 聚合：
   - `total`
   - `avgScore`
   - `perfectCount`
   - `correctCount`
   - `deficientCount`
   - `wrongCount`
   - `unknownCount`
3. 题目矩阵按题目顺序展示结果色块，点击仍进入 ReviewPage 对应题目。
4. 历史趋势调用现有练习历史接口，展示最近若干次 `score` 和 `accuracy`。

视觉方向保持当前项目的暖纸色、墨色文字、棕金和低饱和状态色，不引入重型商业 BI 风格。图表应服务于复盘，不应压过评估文本。

### 3.4 后端处理

第一版不新增专门统计接口。只建议补齐历史接口中的结果字段一致性：

1. `PracticeSessionResponse` 增加 `perfectCount`。
2. `queryPracticeHistory()` 返回 `perfectCount/correctCount/deficientCount/wrongCount/unknownCount`。

当前 session 的模块统计由前端根据 `PracticeDetailResponse.items` 聚合即可。

### 3.5 风险与边界

1. 模块标签可能是逗号分隔的多标签，第一版可按完整字符串聚合；后续如需更准，再拆分多标签。
2. 历史趋势只针对同一题集，不做跨题集能力趋势。
3. 图表不重新解释成绩，不替代 AssessAgent 的文字诊断。

## 4. 需求二：AI 补全时允许用户指定标准答案

### 4.1 问题判断

当前 `/qa/item/complete` 会由 AI 全自动补全答案、知识点、难度、模块标签和来源信息。用户无法在补全时指定自己的标准答案，这会导致面试准备中最关键的“人工裁定答案”被 AI 替代。

V7 应支持用户在重新补全或手动补全时可选输入标准答案。AI 需要围绕该答案补齐其它字段，而不是重写答案。

### 4.2 接口设计

继续使用现有统一入口：

```http
POST /qa/item/complete
```

请求字段扩展：

```json
{
  "id": "qa-item-id",
  "question": "题目内容",
  "answer": "用户指定的标准答案，可选"
}
```

语义：

1. `answer` 为空：保持现有全自动补全。
2. `answer` 非空：把用户答案作为 ground truth。
3. 后端保存时必须强制使用请求中的 `answer`，不能使用 LLM 生成或回传的 answer。

### 4.3 Agent 设计

不建议在一个 prompt 内通过复杂条件分支处理两种场景。V7 推荐拆成两个语义明确的 SubAgent：

```text
CompleteAgent
  -> 判断 request.answer 是否为空
  -> AutoCompleteSubAgent
     或 AnswerBasedCompleteSubAgent
```

#### AutoCompleteSubAgent

适用于用户未提供标准答案的场景，行为与现有 CompleteAgent 基本一致：

1. 输入：question、RAG evidence、userProfile、answerStyle、retryHint。
2. 输出：
   - `answer`
   - `knowledgeNote`
   - `moduleTag`
   - `difficulty`
   - `sourceReliable`
   - `sourceChunkIds`

#### AnswerBasedCompleteSubAgent

适用于用户已提供标准答案的场景：

1. 输入：question、userAnswer、RAG evidence、userProfile、answerStyle、retryHint。
2. 不允许改写 userAnswer。
3. 只输出：
   - `knowledgeNote`
   - `moduleTag`
   - `difficulty`
   - `sourceReliable`
   - `sourceChunkIds`

Java 侧组装最终结果：

```text
answer = request.answer
knowledgeNote/moduleTag/difficulty/sourceReliable/sourceChunkIds = AnswerBasedCompleteSubAgent 输出
```

### 4.4 前端处理

题目详情页的“重新补全”弹窗应增加可选标准答案输入区：

1. 问题输入框默认填当前 `question`。
2. 标准答案输入框默认填当前 `answer`，用户可清空。
3. 用户清空标准答案时，走全自动补全。
4. 用户填写标准答案时，弹窗文案应明确“AI 不会改写该答案，只补充知识点和题目信息”。

### 4.5 风险与边界

1. 用户答案可能和资料不一致，`sourceReliable=false`、`sourceChunkIds=[]` 是合理结果。
2. 用户答案质量可能较差，但 Complete 不负责纠正；如需表达优化，应另做“AI 润色”能力。
3. AnswerBasedCompleteSubAgent 输出结构中不应包含 `answer`，避免误保存。

## 5. 需求三：练习题目自定义筛选

### 5.1 问题判断

当前练习创建以题集为单位，后端已有 `selectedModule` 筛选字段，但 Quiz 页未暴露模块筛选 UI。用户在题库管理或题目详情中更常见的需求是：只练当前题，或只练自己勾选的若干题。

V7 应把练习创建协议标准化为“可选题目 ID 列表”。Quiz 页仍保持整本题集练习，不增加复杂筛选入口。

### 5.2 接口设计

扩展 `PracticeInitRequest` 与 `PracticeRestartRequest`：

```json
{
  "qaSetId": "qa-set-id",
  "mode": "SEQUENTIAL",
  "feedbackMode": "ITEM_BY_ITEM",
  "selectedModule": "Redis",
  "itemIds": ["qa-item-id-1", "qa-item-id-2"]
}
```

字段语义：

1. `itemIds` 为空或不传：按现有规则练完整题集，可继续支持 `selectedModule`。
2. `itemIds` 非空：只练指定题目。
3. `itemIds` 与 `selectedModule` 同时存在时，`itemIds` 优先。
4. 单题练习就是传入一个题目 ID。
5. 批量勾选练习就是传入多个题目 ID。

### 5.3 后端处理

后端创建 session 时需要：

1. 校验 `qaSetId` 属于当前用户。
2. 如果传入 `itemIds`：
   - 去重。
   - 校验所有题目属于当前用户。
   - 校验所有题目属于当前 `qaSetId`。
   - 按前端传入顺序创建 `practice_session_item`。
3. 如果未传 `itemIds`：
   - 保持现有 `qaSetId + selectedModule` 查询逻辑。
4. 不过滤 `completeStatus=PROCESSING` 的题目。
5. 创建练习时仍写入题目快照，后续题目补全变化不影响当前 session。

### 5.4 前端入口

V7 不改 Quiz 页的语义：

1. Quiz 页开始测试：不传 `itemIds`，始终整本题集。
2. Repository 题目列表：可勾选题目后开始测试，传选中 `itemIds`。
3. 题目详情页：增加“开始测试”入口，传当前题目 ID。

### 5.5 风险与边界

1. 选择正在补全中的题允许进入练习，但标准答案可能为空，评估质量由用户承担。
2. 同一题集已有未完成 session 时，仍沿用当前 restart / abandon 语义，避免同一题集多个活跃会话互相干扰。
3. `itemIds` 不应写入 `practice_session` 表，题目范围由已创建的 `practice_session_item` 快照自然表达。

## 6. 需求四：语音输入答题

### 6.1 问题判断

技术面试训练不只是写答案，口头表达是核心能力。语音输入可以让用户用更接近真实面试的方式组织回答，同时不改变后端评分模型。

V7 第一版应把语音输入定位为“输入方式增强”，不是语音评测，也不是音频存档。

### 6.2 前端设计

在 PracticePage 答题区增加语音输入能力：

1. 答题框旁增加语音按钮。
2. 点击后进入识别中状态。
3. 识别文本实时写入答题框。
4. 用户可继续手动编辑。
5. 再次点击或识别结束后停止。

建议封装：

```text
useSpeechInput()
  -> supported
  -> listening
  -> transcript
  -> error
  -> start()
  -> stop()
  -> reset()
```

UI 组件可命名为：

```text
VoiceAnswerButton
```

### 6.3 技术方案

第一版优先使用浏览器原生 Web Speech API：

1. `window.SpeechRecognition`
2. `window.webkitSpeechRecognition`

可以引入轻量封装库降低 React 接入成本，但不接入云端 ASR 服务。原因：

1. 不需要上传音频。
2. 不需要后端存储音频。
3. 成本和隐私风险最低。
4. 能满足“语音转文字答题”的第一版目标。

### 6.4 后端处理

后端不需要任何协议调整。语音转写后的文本仍通过现有接口提交：

1. `/practice/item/save`
2. `/practice/item/answer`
3. `/practice/session/submit`

### 6.5 风险与边界

1. 浏览器兼容性有限，不支持时按钮禁用并显示提示。
2. 识别准确率受系统语言、麦克风和浏览器服务影响。
3. V7 不做语音流利度评分、不保存音频、不做发音分析。

## 7. V7 接口变化汇总

### 7.1 `/qa/item/complete`

请求新增可选字段：

```json
{
  "id": "qa-item-id",
  "question": "题目内容",
  "answer": "用户指定标准答案，可选"
}
```

### 7.2 `/practice/session/init`

请求新增可选字段：

```json
{
  "qaSetId": "qa-set-id",
  "mode": "SEQUENTIAL",
  "feedbackMode": "ITEM_BY_ITEM",
  "selectedModule": "Redis",
  "itemIds": ["qa-item-id"]
}
```

### 7.3 `/practice/session/restart`

请求新增可选字段：

```json
{
  "sessionId": "old-session-id",
  "qaSetId": "qa-set-id",
  "mode": "SEQUENTIAL",
  "feedbackMode": "ITEM_BY_ITEM",
  "selectedModule": "Redis",
  "itemIds": ["qa-item-id"]
}
```

### 7.4 `/practice/session/history`

响应建议补充：

```json
{
  "perfectCount": 1
}
```

使历史练习结果与当前 session 结果字段保持一致。

## 8. 实施顺序建议

### 8.1 第一批：低耦合体验增强

1. 结果页可视化
2. 语音输入答题

原因：

1. 对后端主链路影响小。
2. 用户感知明显。
3. 可独立验证。

### 8.2 第二批：协议和 Agent 能力增强

1. 指定标准答案补全
2. 指定题目列表创建练习

原因：

1. 需要改 DTO、Agent prompt、Repository 查询逻辑。
2. 需要更严谨的边界校验。
3. 对已有接口行为有兼容要求。

## 9. 不做范围

V7 不做以下内容：

1. 不做语音评分、发音分析或音频存储。
2. 不做跨题集长期趋势分析。
3. 不做新的结果统计专用接口。
4. 不做标准答案 AI 润色。
5. 不改 Quiz 页为复杂筛选页。
6. 不调整练习表结构。
7. 不改变 FeedbackAgent 和 AssessAgent 的判分规则。

## 10. 验收标准

### 10.1 结果页可视化

1. 完成练习后能看到五维分布、模块表现、题目矩阵和历史趋势。
2. 图表数据与原始 session/items 数据一致。
3. 点击题目矩阵或题目明细仍能进入 ReviewPage 对应题目。

### 10.2 指定标准答案补全

1. 未传 `answer` 时保持现有自动补全行为。
2. 传入 `answer` 时，保存结果中的 answer 与用户输入完全一致。
3. AI 只补齐知识点、难度、模块标签和来源信息。
4. 题目补全中的并发保护仍然生效。

### 10.3 自定义题目筛选

1. Quiz 页开始测试仍创建整本题集练习。
2. Repository 勾选题目后可只练选中题。
3. 题目详情页可只练当前题。
4. 传入不存在或不属于当前题集的题目 ID 时返回明确错误。

### 10.4 语音输入答题

1. 支持的浏览器中可语音转文字写入答题框。
2. 不支持的浏览器中按钮不可用且有明确提示。
3. 语音和键盘输入可以混合使用。
4. 后端收到的仍是普通文本答案。
